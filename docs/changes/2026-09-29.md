# 2026-09-29

本次两批。起因是一次针对「性能与稳定性」的审计,顺带用**真实的 requests.jsonl**
(8179 条)做了标定,而不是凭感觉挑优化点。

以下只记实际改动与实跑结果。

## 二、长回答的用量被整条记成 0(流式 usage 在末尾,而攒样只留头部)

真实日志标定:8179 条里 **129 条 `status=200` 却 `in=0/out=0`**。逐条看过之后,
其中绝大多数是 `cancelled`/`stream_aborted`(客户端中途断开,usage 本来就拿不到,属正常),
但有 13 条 `err_class` 为空的**成功**请求同样两个 0 —— 且全是流式。

对着转发路径读下去,根因在 Anthropic 直通那条 SSE 分支:

```js
let acc = '';
cres.on('data', c => { if (acc.length < 1024 * 1024) acc += c.toString('utf8'); res.write(c); });
cres.on('end', () => { finishEntry(extractUsageFor(wire, acc)); ... });
```

只攒**前** 1MB。而各协议的 usage 出现位置不同:

| 协议 | usage 在哪 |
| --- | --- |
| Anthropic | `message_start`(头,常给 0)与 `message_delta`(**尾**,真值) |
| responses | `response.completed`(**尾**) |
| chat | 末块带 usage(**尾**) |

也就是说长回答一旦越过 1MB,**末尾的 usage 永远进不了 `acc`**。本机复现(1.54MB 的 SSE,
上游在末尾明确报 `in=12345/out=6789/cache_read=111`):

```
修复前: 日志: status=200 in=0   out=0    cache_read=0
修复后: 日志: status=200 in=12345 out=6789 cache_read=111
```

这不是"少记一点":`requests.jsonl` 是渠道用量审计的唯一依据,而**长回答恰恰是最贵的那批**。

### 改动

`lib/upstream/collect.js` 新增 `headTailUsage(cres, res, fn)`:头尾**各**留一段(各 128KB),
仍然有界,只是把"留哪一段"从"只有头"改成"头尾都留"。转发路径改走它。

两个细节:

- 用 `StringDecoder` 而不是逐块 `c.toString('utf8')`:多字节字符可能横跨两个 chunk,
  逐块 toString 会在边界切出替换字符。回归里用「你好世界」跨过 chunk 边界钉住这一点。
- 透传照旧**原样、逐块**(`res.write(c)` 与攒样共用同一个 `data` 监听,没有拆成两个),
  攒样不改变写出去的形状。

回归用例另外钉住:尾部 usage 在总长超限时仍抠得到、头部 usage 也在、超大流攒样不超过两段上限。

## 一、直连上游此前每次都新建 TCP + TLS 连接

转发时给 `http.request` 传的是 `agent: upstreamAgent(protocol)`,而 `upstreamAgent` 在
**没配 `MIXR_UPSTREAM_PROXY` 时返回 `undefined`**。不显式给 agent 就用 `globalAgent`,
而它的 `keepAlive` **随 Node 大版本变**——探针实测三版:

| Node | `http.globalAgent.keepAlive` |
| --- | --- |
| v18.20.8 | **false** |
| v22.23.2 | true |
| v24.18.0 | true |

也就是说在 **Node 18**(CI 矩阵里跑的那一版)上,每一条转发都是一次全新的 TCP + TLS 握手。
本机实测(同一台机器、零 RTT,`test` 之外的临时脚本):

```
HTTPS  新建连接 4.93ms/次  →  复用 0.66ms/次
HTTP   新建连接 1.03ms/次  →  复用 0.47ms/次
```

这只是**握手本身**。真实上游在 WAN 上,TLS 握手是 1~2 个 RTT(100~400ms 量级),
而每一次对话请求——含每一轮子代理、每一次标题生成、每一次 `count_tokens`——都要付一遍。
隧道那条路径一直是 keepAlive(`createProxyAgents` 里就写着),反倒只有"直连"这条
**主流**路径在重连。

端到端核对(改造后,Node 18,同一进程内 mock 上游):连打 5 次 `/v1/messages`,
上游侧 `connection` 事件只发生 **1** 次。

### 改动

`lib/upstream-proxy.js` 新增 `directAgent(protocol)` 与 `transportAgent(protocol)`:

- `directAgent` 按协议各建**一个** `keepAlive` agent(`maxSockets: 128`、`maxFreeSockets: 32`)
  并缓存。SSE 流会长期占住 socket,128 给并发对话留余量;不设上限则是一个打爆上游的敞口。
- `transportAgent` = 配了隧道走隧道,没配也**仍然复用连接**(而不是回落到 `globalAgent`)。
- 两条出站路径都改走它:真实转发(`mixrouter.js` 的 `transport.request`)与渠道探活
  (`lib/upstream-probe.js`)。`upstreamAgent` 职责不变——它只回答"配没配隧道",
  `upstream-probe-check` 靠它短路。

### 一个必须记下来的坑:空闲连接会吊住退出

复用一上来,Node 18 上整套测试就**全绿但不退出**(挂在 `run-tests.js` 的硬截止上),
`modules-wiring.test.js` 尤其明显:24 项全过,进程不退。

根因是 Node 18 的 `server.close()` 要等空闲 keep-alive 连接走完 `keepAliveTimeout`
(默认 5s)才回调,而 `globalAgent` 在 18 上恰恰**不** keepAlive——所以这个坑是本改动
第一次把 keepAlive 带上主流路径时才出现的。三版对照实测:

```
v18.20.8  close() 回调耗时 4506ms(要等 agent.destroy())
v22.23.2  close() 回调耗时    2ms
v24.18.0  close() 回调耗时    1ms
```

两条路都试过,**第一条是错的**:

- ❌ **`Agent` 构造器的 `timeout` 选项**。它连**在途** socket 一起管,而本进程的流式转发
  允许上游长时间静默(README 里 `MIXR_STREAM_IDLE_TIMEOUT_MS=90s` 就是为这段静默留的)。
  实测构造形状:上游发完 SSE 头后静默 3 倍阈值再补内容——用 `timeout` 那一版**直接触发
  请求级 timeout、流被掐成 aborted**,后续内容全丢。这是会**伤到真实转发**的错法。
- ✅ **只给空闲 socket 计时**。用 `Agent` 的两个既有扩展点:
  `keepSocketAlive`(交还池子、变成空闲时)开始计时并 `unref`,
  `reuseSocket`(被取出使用时)立刻清零。在途请求完全不受影响。
  实测同样形状:静默 3 倍阈值仍收到完整流;空闲到点后连接自己退场,两端一起释放。

阈值默认 5s(与 Node 自己的 `keepAliveTimeout` 同值),可用 `MIXR_UPSTREAM_IDLE_MS` 覆盖。
连续对话里一轮接一轮的间隔远小于它,常见形状照样复用。

隧道那条路径的 agent 也一起装了这套(`createProxyAgents`):它原本就 keepAlive,
一样会把夹具/进程吊在 `keepAliveTimeout` 上。

### 收尾

`mixrouter.js` 收到 SIGTERM/SIGINT 时,在 `lifecycle.stop()`(**排空在途响应**)之后
调 `destroyAgents()` 再退出——排空阶段还要用这些连接转发,提前销毁会把在途响应掐断。

## 验证

- `npm test`,Node v18.20.8 / v22.23.2 / v24.18.0 三版各 **869 项全绿**
  (较改动前 +4 项:三条连接复用回归 + 一条 headTailUsage 回归)。
- `npm run smoke`(Node 18):**18/18 通过**。
- 连接复用新增三条回归(`test/upstream-proxy.test.js`),分别钉住:
  1. 直连复用——同一上游连发 4 次只建 **1** 条连接(这条在 Node 18 上改动前会得到 4);
  2. 空闲连接能自行退场——空闲阈值到点后 `close()` 必须远快于 `keepAliveTimeout`;
  3. **在途的流式静默不得被误杀**——上游发完头后静默超过空闲阈值再补内容,
     收到的必须是完整流。第 3 条钉的正是上面那个"错的解法",防止日后有人把
     `timeout` 选项加回来。
- 用量修复新增一条回归(`test/modules-wiring.test.js` 的 `headTailUsage` 用例):
  尾部 usage 在总长超限时仍抠得到、头部 usage 也在、逐块透传原样、跨 chunk 多字节字符不坏、
  超大流攒样有界。
- 端到端核对(临时脚本,未进仓库):连打 5 次转发,上游只收到 1 条 TCP 连接;
  1.54MB 的流末尾 usage 落盘正确。

## 已知边界

- 连接复用只影响**出站方向**。入站(客户端到本代理)的 keep-alive 由 Node 自己管,未改动。
- 空闲阈值以下的间歇请求仍复用;超过阈值则新建连接。这是有意的取舍:
  宁可偶尔重连,也不留一堆陈旧 socket(上游可能已单方面关闭它们)。
- `maxFreeSockets: 32` 是**按 host** 计的,不是全局;渠道多时池子会按上游分散。
- `headTailUsage` 的两段之间可能有缺口(超长流的中段被丢掉)。这对 usage 无语义影响
  (匹配取"末次出现",真值在尾段),但**不要**拿它去解析流内容——它只为抠用量而生。
