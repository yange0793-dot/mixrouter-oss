## 1. 执行摘要

### 1.1 现状判断

**mixrouter 不需要换栈重写，需要先修复请求编排的可靠性缺口，再收拢模块边界和控制台交互。**

项目已经具备清晰的差异化能力：

- 会话级粘性分发及会话级 Key、槽位覆盖。
- Claude 五槽、Codex 自定义槽位及主链/子代理双通道。
- 同一进程中的协议转换、工具调用与 thinking/reasoning 往返。
- 上游健康、预算和取消收尾，以及独立的压缩模型、Key 和上下文窗口设置。

68 个库文件的本地静态 `require` 图没有检出的循环依赖，已有拆分方向总体成立。真正的问题不是"文件不够多"，而是：

1. `proxyHandler` 约 781 行，同时拥有候选选择、重试、多个定时器、协议分支、健康许可、取消、会话写入与日志终态。
2. 部分模块自身已有测试，但主入口接线没有完整覆盖。
3. 184KB 控制台的全局状态、草稿、轮询和内联事件相互牵连。
4. 开发目录同时是生产运行目录，代码、静态页面、PID、日志和部署脚本存在路径耦合。

本轮直接确认的首要问题包括：

- `health.acquire()` 返回 `null` 后仍能发送请求，导致熔断拒绝被绕过。
- 收到 200 响应头就记健康成功，随后断流无法修正已经结算的成功。
- 本地 `count_tokens` 估算被记作一次网络尝试和一次健康成功。
- Codex→Chat 的 SSE 和 JSON 两个调用点均没有传原始请求上下文。
- 仓库只 fetch `main` 的非标准 refspec 会隐藏其他分支的远端引用状态。

### 1.2 主线与不可变边界

继续采用：

- 零运行时依赖。
- Node ≥18。
- 原生浏览器 HTML/CSS/JavaScript。
- WKWebView 外壳。
- 不引入前端构建步骤。

主线是：

> 请求与会话识别 → 唯一、可解释的路由计划 → 有预算的上游尝试 → 协议转换与转发 → 一次性终态结算。

**四组核心功能全部保留，对话绑定保留并优化。** 不因重构减少现有业务能力；身份、临时绑定和显式配置分层。低收益策略先移出默认界面、保留兼容，不把“当前样本未使用”当作立即删除能力的充分理由。

保留范围不限于四组创新：已有多 Key 管理、客户端接入/配置切换、内容规则、工具过滤、图片处理与识图中继、配置备份恢复、日志/健康/诊断及离线故障验证均纳入兼容清单。删除的是重复实现与误导性表达，不是顺手删掉已有功能。

### 1.4 最大风险

**最大风险是把在线长会话当成可随时重启的开发服务。**

当前优雅退出路径硬编码最多排空 2000ms，并为落盘保留至少约 1000ms；`mixctl stop()` 则在约 4000ms 后可强杀。这是相互约束的预算，不是两个可任选的"2 秒/4 秒档位"。数分钟的在途请求不能依靠这个退出窗口完成。

本次收尾只更新规划文件，不再操作远端，不修改运行代码、配置或基线取证时的在线服务（当时 PID 435；上线前须重新识别，不能照抄旧 PID）。实施期间使用独立开发副本；首次上线只在用户授权的空闲窗口进行，不宣称现有架构支持无损热切换。

- `RequestPlan`：端点、客户端协议、模型输入、会话身份与覆盖快照、匹配来源、候选及模型、Key 约束、stream、请求体引用。

1. 只有 `runAttempts` 决定下一次尝试。

5. 任何已发出的有效客户端响应字节都会关闭透明重试窗口；keepalive 不能抢先提交。

### 2.5.1 修订：不采用 ES module（2026-10-17 实测）

上面"再按页面迁到 ESM"这一条**已作废**，实测与本节自己的验收条件直接冲突：

- `test/ui.test.js`（51 例）与 `test/session-routing-ui.test.js`（27 例）把控制台脚本放进 `vm.createContext(...)`，再用 `vm.runInContext('compactDraft.provider')` 这类方式**直接读写脚本顶层的 `let`/`const`**，两处合计约 410 处断言。
- ESM 顶层绑定进的是**模块作用域**，不落 realm 的全局词法环境：实测 `vm.runInContext('view', ctx)` 报 `ReferenceError: view is not defined`；`m.namespace` 能取到导出，但那是快照式取值，且 ESM live binding **从外部不可赋值**。
- 因此改用 ESM 会打瞎这 410 处断言，正是本节末段禁止的"删除…测试来换取拆分顺利"。附带代价还有 `--experimental-vm-modules` 这个运行时开关（本项目 Node ≥18、零依赖、CI 需复现，不该引入）。

**替代做法（已实证）**：按页拆成**多个 classic script，在同一 realm 内依次执行**。实测跨文件读 `let` 成功、写后立即可见；且**同一顶层名字在两个文件里重复声明会当场 `SyntaxError`**，等于白送一道"每个顶层绑定只有一个家"的安全网。当前 `public/js/app.js` 顶层 204 个声明**零重名**，且已有 `// ---- 渠道 ----` 这类分节注释，边界与模块几乎一一对应，拆分是机械的。

顺序随之改为：外置 CSS/脚本（已完成）→ 按页拆多个 classic 脚本 → 用 `addEventListener`/受控委托逐步替换 95 处内联事件。**"无构建步骤"的约束不变**。

## 3. 核心功能保留与优化方案

### 3.1 会话级分发与会话级 Key/槽位覆盖

**保留理由：同一对话保持渠道与缓存亲和，同时可单独改变该对话的账号和子任务落点，不污染全局配置。这是区别于单纯配置切换器的核心价值。**

当前落点：身份在 `<线上仓库根>/lib/session/identity.js:94`；绑定在 `<线上仓库根>/lib/routing/sessions.js:117`；覆盖校验及 Key 选择在 `<线上仓库根>/lib/routing/session-config.js:23`、98；revision 保存位于 `<线上仓库根>/lib/http/console.js:558`；入口快照及尝试时 Key 重查位于 `<线上仓库根>/mixrouter.js:790`、977。

**明确判断：机制值得保留；身份推断、临时绑定、用户配置与池负载统计混在一起的当前形式不值得原样保留。**

取证期间两次累计样本分别为 5948 与 6019 条：首次 `round_robin` 5931 / `priority` 17、header 5947 / fingerprint 1；稍后 `round_robin` 6001 / `priority` 18、header 6018 / fingerprint 1。日志仍在增长，这不是同一固定截止时刻的两次计数。首次记录范围为 2026-10-14T02:01:13.583Z 至 2026-10-16T11:34:48.011Z；第二次未固定截止时刻，不据此计算精确趋势。当时磁盘有 16 个绑定，均为 header，零 pinned、零 Key/槽位覆盖。

**样本只说明本机当时的使用情况，不代表功能对所有用户的价值。** 显式覆盖仍按用户要求完整保留；低频策略仅作界面分层依据，不作立即删除依据。

| 项目 | 删/留/改 | 依据与执行办法 |
|---|---|---|
| header/metadata 稳定身份 | **留** | 完整 ID 作内部键；短 ID 仅显示，不能反过来作状态键 |
| 自动 sticky 绑定 | **留** | 减少跨渠道抖动和缓存损失；只作用于合格候选，不劫持槽位或压缩 |
| 会话 Key/槽位覆盖 | **留** | 只存 ID，不改渠道 `active_key`、不写客户端全局配置 |
| 手动渠道 pinned | **留并改说明** | 与固定 Key 的硬约束不同；明确当前优先绑定及转移条件，不偷偷更改语义 |
| `round_robin` | **留** | 已有实际使用，负责新会话分配；同一会话后续仍 sticky |
| `priority` | **留** | 必要的主备语义，尤其适合槽位后备池 |
| `weighted` | **留在高级设置** | 能表达配额/成本比例，现有实现小且有测试；不能仅因两天样本零用量删除 |
| `least_used` | **改：保留兼容，移至高级设置** | 标注为“按绑定数选择”，不得宣传成按实时负载选择；`activeCount` 不是在途请求、token 或成本。旧配置保持语义，本轮不升级成复杂负载调度器 |
| `random` | **留在高级设置** | 默认推荐轮询；保留旧配置和可选能力，不仅凭本机零使用就删除 |
| 内容 fingerprint 兜底 | **改为显式兼容选项** | 同 system+首条用户文本会合并不同会话，提示变化又会拆开同一会话；默认不得据此新建持久 Key/槽位覆盖 |
| anon/cx-anon | **改** | 无可靠身份时按请求级路由，不把全部匿名请求当一个可持久配置的对话 |
| 12 小时 TTL | **留数值、改作用对象** | 自动绑定按闲置回收；显式覆盖不受 TTL 删除，手动配置须明确保留政策并受容量上限约束 |
| 请求数/token 统计 | **留并限定口径** | 表示代理观察请求及上游申报用量，不等于账单或实时负载；与兼容策略使用的绑定数分开说明 |

本轮不删除策略枚举、不静默替换已有值。普通界面突出 `round_robin` / `priority`，其余放高级设置，现有高级策略必须仍能看见并编辑。以后确需删除某项，应另列弃用说明、配置差异预览和可逆迁移，不能夹带在模块搬迁中。

当前问题还包括：`sessions.js:24` 同时保存绑定、游标、冷却；`prune` 按 `hasRouting` 豁免，却没有把手动配置与自动记录全面区分；配置保存与在途请求完成共享会话记录，必须防旧状态复活。

优化：

1. 分开自动 binding 与显式 routing，以及池运行状态。
2. 页面分别显示配置要求、当前绑定、最近实际落点，不用一个"已绑定"混称。
3. 保持入口覆盖快照；每次尝试按 ID 重新确认 Key 有效。固定 Key 失效明确失败，不悄悄换账号。
4. 保留 revision、409 和未保存草稿；轮询不覆盖编辑。
5. 显式配置受容量限制，不能靠 TTL 静默清理；低可信身份明确提示，已有兼容配置不暗中迁移到另一个会话。

**验收**：两个并发会话的账号/槽位互不影响；标题、子代理、压缩不污染主对话；Key 停用/删除不串账号；中途编辑/解绑后旧响应不复活状态；匿名或低可信身份不能创建易串用的持久覆盖；重启保留显式设置，自动绑定按 TTL 回收。

### 3.2 槽位路由与主链/子代理双通道

**保留理由：稳定客户端别名与真实模型解耦，主链、子代理及其他档位可以独立调整，不要求客户端认识所有渠道。**

落点：五槽常量与 env 映射在 `<线上仓库根>/lib/routing/slots.js:30`；候选池和主渠道置首在该文件 92–135 行；主链/子代理补丁在 189–228 行；真实匹配顺序位于 `<线上仓库根>/lib/routing/resolve.js:6`。

当前问题：部分注释写"槽位优先一切规则"，与实际内容规则先行不符；会话槽位覆盖后，入口又从全局槽表读取 `dropTools` 等字段，继承规则不够显式；UI 槽名容易被误读成真实上游模型身份。

真实顺序必须保留并讲清：**内容规则 → 会话覆盖后的槽位 → 普通规则 → default**。压缩要先于主槽，普通模型名子串规则则不能截走槽位。

保留：Claude main/opus/sonnet/haiku/subagent 五槽，不恢复已移除 fable 槽；Codex 自定义槽；pool/strategy/dropTools；主链与子代理独立；会话覆盖与全局槽位并存；切换时保留仍兼容的备池及工具过滤，不能保存一次就静默抹掉字段。

优化：

1. resolver 返回统一 `source`/`effectiveSlot`，入口不再隐式拼合两套来源。
2. 明确会话槽位如何继承 `dropTools` 等全局属性；需更改语义时单独提交并给迁移说明。
3. UI 同时显示主目标、后备、wire、最近实际落点；"opus"只是槽名，不保证真实上游型号。
4. 预览与入口复用 prepare，测试内容规则、会话覆盖、全局槽位、普通规则冲突矩阵。

**验收**：普通规则不截槽位；压缩先于主槽但不改普通会话绑定；同会话 haiku/子代理不污染下一轮 main；priority 主渠道始终位于池首；Codex 自定义槽不被 Claude 清理删除；日志同时保留 `model_in`、`model_out`、`slot`、`provider`、`wire`，凭实际请求判断落点。

### 3.3 进程内协议转换与 thinking/reasoning 往返

**保留价值：转换共享路由预算、取消和日志闭环，避免独立转换代理的额外故障域。** 实现在 `<线上仓库根>/lib/wire-responses.js:1`、`<线上仓库根>/lib/wire-chat.js:1`、`<线上仓库根>/lib/wire-openai-bridge.js:170`。

当前问题：`<线上仓库根>/mixrouter.js:1349` 的 `streamChatAsResponses` 和 1358 行的 `chatJsonToResponses` 均漏传 `request`；工具注册表取不到 `request.tools`，SSE 路径的 `request.stream` 默认恒按 `true`，破坏非流请求。**helper 单测不证明入口正确。**

保留：现有协议能力矩阵、AnthropicStream 终态纪律、工具参数校验、reasoning content/summary 特例和缓存 usage 去重。**不是任意六方向全互转；原生 Responses compact 不能硬塞 Chat。**

优化：第一期补两个调用上下文及入口测试；转换器只报告完整性/错误，不决定健康或切渠道；集中可测试的模型特例，不另造通用 IR 或插件框架；**缺失用量不得冒充确定零消耗。**

**验收**：真实入口覆盖 SSE/JSON、`stream:false`、上游忽略 stream、custom tools 及下一轮结果、thinking/reasoning 往返、200 包 error、缺终态和残缺工具参数；提交前可重试，提交后不重播；正常、取消、中断各只结算一次。

### 3.4 上游健康与压缩专用路由

**保留价值：健康/预算/取消减少无效消耗，压缩独立模型与 Key 使上下文维护不绑死于主模型成本和可用性。**

当前健康问题位于 `<线上仓库根>/mixrouter.js:1022`、1234、1016/1028：`acquire=null` 不拦截；200 头提前 success；本地估算计 attempt+success。**健康实际参与选择并跨请求累积，不能说"只用于控制台"**；但 `strategy:31` 全池兜底、`sessions:128` 钉定只查 cooldown、后备/重试与并发状态变化都能绕过软筛选。准确严重度是：**熔断拒绝可被稳定绕过，全池故障与半开并发保护不可靠。**

优化：以 `acquire=null` 时**跳过成员且不计 network attempt 为硬闸门**，`eligible` 过滤仅作优化；重试重新取许可，全池无许可明确失败；success 推迟至有效协议终态；本地估算移到许可/计数之前；取消不计成功失败；每 attempt 幂等归还许可、清定时器，request 只结算一次。**达到熔断阈值后不为维持旧测试的"四次"而强行续打。**

超时：现网五个超时均 900000ms，配置与活进程已核对一致。**保留用户数值**，只显示来源与动态总预算；不同默认值与部署值差异不同，**不能统称 15 倍**。

压缩实现在 `<线上仓库根>/lib/routing/compact-signature.js:1`、`<线上仓库根>/lib/routing/compact.js:1`、`<线上仓库根>/lib/compact-window.js:1`。保留全局/项目专用规则、独立模型/Key、固定 Key 失效明确报错、用户/项目/local/环境分层，以及**写盘成功 ≠ 旧客户端即时生效**。

压缩优化：升级客户端时维护真实签名样本和反例；只在真实压缩指令位置判断，不扫历史/工具结果；预览说明规则与 Key 来源；UI 分开模型路由、窗口数值、生效范围。

**验收**：半开最多一个实际探测，无许可零网络调用；200 后中断不清失败；本地估算 attempts=0；取消不污染健康；各超时有唯一终态；引用压缩原文不误命中、末尾 system 通告不漏命中、专用 Key 不串账号、层级覆盖准确、**旧会话不被宣传成已热更新**。

## 6. 风险、旧问题处置与回滚

### 6.1 开发隔离与首次上线顺序

1. **先固定源码证据。** 记录 HEAD、分支、工作区和远端引用；保存可验证的源码归档或 Git bundle。bundle 不包含未跟踪文件，规划等必要文件须另存。修正 fetch refspec 是单独的本地仓库设置操作，不能把未出现远端跟踪引用误判为推送失败。
2. **再建立独立开发副本。** 建议普通 clone 到未占用的 `mixrouter-dev` 目录；如目录已有内容先检查，不能覆盖。开发仅用假 Key、假会话和本地上游，复用项目既有隔离测试脚本，不复制现网凭据来图方便。
3. **备份区与开发区分开。** 在线配置和客户端配置备份含敏感信息，应存仓库之外的受限目录；保存权限和校验记录，不写进 Git 或制品。在线逐文件读取不能保证跨文件一致，只能标注为初步副本，不能冒充可事务恢复的快照。
4. **离线候选通过后再约上线窗口。** 检查现时 PID、启动方式、在途请求和端口，不照抄本文件历史 PID。停止新工作并等待在途请求结束；不能仅凭一次“活跃数为零”就保证之后不再有新流量。
5. **授权窗口内停止旧服务，再制作最终一致备份。** 使用实际进程管理方式保证 launchd 不立即拉回旧进程；确认旧写入者已退出，再备份、迁移并验证配置。保留原目录，不删除旧数据。备份无效或无法解析则停止迁移。
6. **启动确定版本并验证。** 发布代码、静态资源和数据路径须明确；确认没有两个进程写同一数据目录。检查健康端点、源码/UI 修订、配置数量和引用，再进行授权范围内的请求验证。
7. **失败则回退代码与启动配置。** 数据格式兼容时沿用当前数据；不兼容时使用事先验证的逆向转换或恢复方案，并单独处理上线后的新增设置。无法无损处理时停止自动回退，保留全部现场，不覆盖后续写入。

现有退出窗口不足以排空长会话；`mixctl` 的强杀计时不适用于所有 launchd 操作。**本轮不承诺零停机或无损热切换，也不为重构擅自改在线超时值。** 在第四期部署解耦前，前几期完成只意味着候选代码可交付；如需提前上线，同样必须安排授权空闲窗口。

### 6.3 opus 槽位现场拒绝的处置边界

规划期间曾有一次请求经 opus 槽位收到上游 HTTP 500，错误文本为 `sensitive words detected`；后续请求成功。**这只能证明该次上游返回拒绝，不能证明规划内容违法、模型永久不可用，或本地路由器已经损坏。槽位名也不证明真实上游型号。**

处理方向：

- 保留原 HTTP 状态、渠道、实际模型、attempts 和脱敏错误摘要；不把它概括为普通“网络断开”。
- 不因单次拒绝改主链、子代理、effort、压缩或 Key 配置。
- 如果上游提供可靠的结构化拒绝标识，可将其区分为不可原样重试的结果；仅有自由文本、错误含义不明确时不能建立全局关键词规则。
