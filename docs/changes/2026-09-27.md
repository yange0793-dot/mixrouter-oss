# 2026-09-27

本次做两批:

一是让**渠道库(providers.json)终于有备份**、修掉一条**预警自己报错数**的缺陷、
落盘前清掉会污染备份池的临时残留。

二是一批同病缺陷:**落盘失败时接口说"失败",而状态已经生效了一部分**。四条路径各修一处
—— 删渠道的失败回滚只回滚了三处状态里的一处、`PUT /api/slots` 与 `PUT /api/routes`
是先改内存后落盘、`POST /api/claude/split` 的 `apply` 会**在渠道库落盘失败之后仍然改掉
用户自己的 `~/.claude/settings.json`**。最后一条最贵:它动的是仓库之外的文件。

以下只记实际改动与实跑结果。

## 渠道库此前是这个仓库里唯一没有备份的活文件

`providers.json` 装**全部渠道的明文 api_key**。客户端配置(`settings.json` /
`config.toml` / zcode config)每次改写前都 `backupFile` 一份,唯独它没有 —— 而
`lib/backup/targets.js` 早就把它列成一个备份池(`[data]`),`GET /api/backups` 与
`mixctl backups` 都在报它。

探针实测(`/tmp` 下的临时脚本,未进仓库):建两个渠道 + 改一次,`data/` 里**只有
`providers.json`,零备份**。那个池子从建成起就恒为 0 份 —— 面板上看着"这里有备份在管",
实际是**永远不会有**。清点报的是"这里查过、没有",读起来像"目前还没有备份"。

改动收在**唯一的落盘点**上,而不是散到四个调用点(`withStoreRollback`、拆分配置、
删渠道时的清引用、退出前的收尾落盘):

- `lib/atomic-write.js` 的 `writeJsonAtomic` 新增**显式** `backup` 选项。默认 **off**:
  `saveSlots` / `flushSessions` 是高频路径,给它们各复制一份是把写放大塞进热路径。
  开启时委托给 `backupFile`(`lib/config-backup.js`)—— 名字模板与保留池规则是全仓共读的
  一套契约,不在这里造第二套。`keep` 与 `onWarn` 原样透传。
- `mixrouter.js` 的 `saveStore` 开 `backup: true`。四个调用点仍旧只写一次 `saveStore()`,
  备份跟着它走。落盘失败的回滚行为(磁盘写不动就回滚内存)一字未动。

两个附带结果,都是这条路径本来就该有的:

- 备份与**轮换预警**都发生在原子替换**之前**,所以"这一次顶掉了谁"说的是真事(见下条)。
- 首次保存时活文件还不存在,`backupFile` 返回 `null`、什么都不做 —— 这是它的既有约定
  ("没有旧内容可备份"),不是漏备。

## 备份池预警报的份数是错的:同一个新名字被数了两遍

`lib/backup/pool-watch.js` 的 `planDeletion` 文档里写着 `newName` 是"**将要**写入、
盘上还没有"的名字,于是实现把它 `concat` 进池子再算一遍。但唯一的调用方
`lib/config-backup.js` 一直是**先 `copyFileSync` 落盘、再调预警** —— 那一刻新名字
**已经**在池子里,被数了两次。

实测(在**改动前**的树上跑,`git archive HEAD` 解出来的干净副本):

```
盘面:5 份 providers 备份 + 3 份别的活文件的备份(同目录),保留上限 5
预警原文:[backup] 保留池已满(6/5):本次备份将顶掉 2 份 —— …0101…、…0102…
实际:备份后池子仍是 5 份 ⇒ 真删了 1 份
```

三个数里两个是错的:份数 6 其实是 5,"顶掉 2 份"其实是 1 份,而"**已满**"更是不成立
(5 份正好等于上限)。池子每多一份,这个数就多错一份 —— 而它正好被上一条改动带进了
日常路径:现在**每次保存渠道**都写一次库。

契约与实现分叉了却没人发现,是因为**注释与自测都照着契约写**:五处说明和五条用例都把
newName 当成"盘上还没有"的名字(用例里那个名字也确实没落盘),于是它们复现的是一个
不存在的调用形状,把一个真缺陷供了起来。

改法是把契约按**实现的实际形状**定死(copy 之后),两端一起改:

- `planDeletion` 不再 `concat`:池子就是此刻的 `readdir` 结果,与 `backupFile` 马上要
  拿去删除的那个池子是同一个。报出的份数 = 用户 `ls` 能看到的份数,也 = 随后真会删的份数。
- 顺带修掉措辞:`保留池已满(${poolSize}/${keep})` 把份数当成了"满没满"的判据,
  池子根本没满时它也在喊。现在两件事分开说 —— 池子多大就报多大,要删几份由删除集合
  自己说;没有任何东西要被删时**一句都不出**(与 `backupFile` 的沉默条件一致:
  备份不会删东西时,预警也不该出声)。
- `newNameVisible` / `newNameIsOurs` 报给调用方:若哪天预警又被排到 copy 之前,
  它会直接说出来,而不是默默算一个对不上的集合。
- 五条按旧契约写的用例改成真实形状(`newName` 先落盘),另加两条:删除份数**随池子大小
  单调变化**(只验"有没有 warn / 名字在不在"的话,份数报错一倍照样绿),
  以及**池子恰好等于上限时是沉默的**。

## 落盘前的临时残留会占备份池名额,内容是半截的

`writeJsonAtomic` 的临时文件名是 `<file>.<毫秒>-<32 位十六进制>.tmp`。进程被 SIGKILL 时
`finally` 不执行,它原地留下。它本身良性(唯一名,不会让下一次写入失败),但**会被备份
卷进去**:名字顶在 `providers.json.` 前缀上,于是占一个 `keep` 名额,还能顶掉一份真备份;
而它的内容是**上一次写入没写完的那一半** —— 备份池最老那份被换成半截 JSON,而"备份"
这个词让人以为捡回来的至少是个完整文件。

`writeJsonAtomic` 在备份**之前**清掉本目标自己的这类残留(精确匹配本模块产出的名字,
不碰 `*.bak-mixui-*`、不碰别的目标、不碰目录),并把清掉几份经 `onWarn` 说出来。
清理是尽力而为:单个删不掉(权限、只读目录)就跳过,永不让这次配置写入失败。

## 删渠道失败时只回滚了一处(HTTP 说"删除失败",盘上槽位已经空了)

`DELETE /api/providers/:id` 会动**三处**状态:渠道库、槽位表、路由规则。它的失败回滚
原本只做了第一处:

```js
catch (e) { store[app].push(removed); return sendErr(500, ...); }
```

而槽位与路由的引用是在 `saveStore()` **之前**就摘掉、并且**已经各自落盘**的
(`saveSlots` / `saveRoutes`)。所以这条路径实际做的是:把渠道放回内存,而盘上对它的引用
已经没了 —— 而 HTTP 回的是 500「删除失败」,用户以为什么都没发生。

实测(探针,让原子替换那一步抛 `EIO`):

| | 删除前 | "失败"之后 |
| --- | --- | --- |
| 渠道 | 在 | 在(回滚对了) |
| 槽位 `subagent` | `{provider: <id>, model: 'm'}` | `{provider: '', model: ''}` |
| 路由规则 `r1` | `provider: <id>` | `provider: ''` |

槽位连 `model` 都丢了。重启之后:渠道回来了、绑它的槽位是空的。**回滚只做一处比不做更坏**
—— 它让人以为已经回滚过了。

改法是三处一起快照、一起回滚,并且回滚要把槽位与路由**重新落盘**(它们在过程中已经写过盘):

- 快照必须在 mutate **之前**取,而且必须**深拷贝**。这一条踩过一次:槽位的摘除是
  `delete slotMap[g][name]`,**原地改嵌套对象** —— 快照存引用的话,回滚时拿到的是那个
  已经被改过的对象(实测:渠道与路由都回来了,唯独槽位还是空的)。
- 回滚自身若也失败,不能回一句"删除失败"了事:那时盘上是不一致的,响应里要把
  "盘上已不一致,请检查 slots.json 与 routes.json"如实说出来。

## 落盘失败时"说失败、却已经生效":槽位与路由

同一批探针还查出两条**同病**的写路径。它们的形状是"先改内存、再落盘",落盘失败时接口回
500,而内存里已经是新值 —— 而**读内存的正是转发**:槽位解析读 `slotMap`,路由匹配读 `routes`。

实测(探针,让原子替换那一步抛 `EIO`):

| 接口 | HTTP | 盘上 | 内存 |
| --- | --- | --- | --- |
| `PUT /api/slots` | 500 | `subagent.model = ORIGINAL` | `CHANGED` |
| `PUT /api/routes` | 500 | `r1.match = ORIGINAL` | `CHANGED` |

也就是说:弹窗说"保存失败",新槽位/新规则**当场就已经在生效了**;重启之后盘上是旧的,
又"改回来" —— 用户看到的是"过一会儿它自己变回去了"。

改法与 `withStoreRollback` / `configureClaudeSplit` 一致:**先落盘、成功了再提交到内存**。

- `PUT /api/slots` 在副本上改完再落盘,失败就丢副本(`slotMap = prev`)。副本用
  `structuredClone` 而不是浅拷贝 —— 改的是 `next[app][name]` 这些嵌套对象,共享引用就白改了。
- `PUT /api/routes` 先把 `next` 落盘,失败直接返回;成功才 `routes = next`。
  `saveRoutes` 因此多了个可选参数(默认仍是当前 `routes`),好让它能写"还没提交的那份"。
- 两处的错误文案跟着分开了(`写入槽位失败` / `写入路由规则失败`),以前它们冒泡成裸的
  `{"error":"simulated"}` —— 用户看不出是哪一步没成。

顺带踩到一个**测试脚手架的坑**,记下来免得下次再撞:这个仓库有两条**源码级扫描**
(`test/log-wiring` 与 `test/request-log`)会把源码里任何"entry 点某字段 后跟赋值号"的形状
当成日志条目的字段写入,拿去和日志白名单比对,而且**它们不剥注释**。我第一版把槽位副本的
局部变量命名成 `entry`(以及顺手在注释里写了那个形状),两条扫描当场报出一个叫 `X` 的
"越界字段" —— 那不是真字段,是扫描器把标识符当成了字段名。变量改名、注释改措辞即可。
这个坑值得留着:它是**假阳性**,而假阳性会教人忽略真阳性。

## 落盘失败时"说失败、却已经生效":应用槽位(最贵的一处)

同一条探针扫到的第三处,也是最贵的一处:**`POST /api/claude/split` 的 `apply`**。
它一次动三处状态 —— 渠道库的 `current`、**用户自己的 `~/.claude/settings.json`**、内存 `current`
—— 而代码的顺序与它自己那句注释**正好相反**(注释写"路由先持久化,再改客户端",代码是先改客户端、
再 `saveStore()`)。

实测(探针,让原子替换在 `providers.json` 上抛 `EIO`):

| | 失败前 | 接口回 500 之后 |
| --- | --- | --- |
| HTTP | — | `{"error":"simulated"}` |
| 用户的 `settings.json` | `{"env":{"KEEP":"me"}}` | **已被改成路由模式**:`ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN` 与全部 `mixr-*` 槽位别名(9 个键)都写进去了 |
| 内存 `current` | `null` | `@router` |
| 盘上 `providers.json` 的 `current` | `null` | `null` |

用户看到的是"应用槽位失败",实际他的 Claude Code **已经被指到本机代理上**,而渠道库不知道这件事
—— 重启之后从盘上读回来的 `current` 仍是 `null`,客户端却还指着 `:8787`。这条路径改的是
**仓库之外**的文件,所以它是这一批里代价最高的一处:前三处最多是"盘上与内存不一致",这一处是
"用户的客户端被改了,而他以为没改成"。

改法照 `PUT /api/slots` 那条:**先落盘、成功了再动下一步**,每一步各自带回滚。

- 顺序改成 `saveSlots()` → `saveStore()` → `switchClaudeRouter()`。前两步失败时,除了回滚
  `current`,还要把 `slotMap` 与盘上的 `slots.json` 一起退回去 —— 否则"应用失败"之后槽位表
  里已经多了一套指向新渠道的槽,而渠道库那边什么都没变。
- 客户端配置**不需要**旧内容快照:`switchClaudeRouter` 的写入是 `writeFileAtomic`
  (要么整份换成新的、要么原样不动),而它后面**没有任何可能抛出的语句** ——
  所以它一旦抛,抛的就是"原子替换本身失败",那时文件还是旧的。第一版为此存了一份
  `before.settings` 并把 `fs` 读进来,是**死代码**(`fs` 也是从这一行才引入的),删掉了。
- 错误文案分开:`写入渠道库失败: …` / `写入客户端配置失败: …`。此前两处都冒泡成裸的
  `{"error":"simulated"}` —— 用户看不出是哪一步没成,更看不出"客户端配置有没有被改"。
  `/api/claude/split` 因此自己接了一层 `try/catch`(走 `sendErr`),不再依赖最外层那个
  只回 `e.message` 的兜底。
- 顺带把 `switchClaudeRouter` 的返回值接住:它带的是**客户端配置**的备份池轮换预警,
  此前这条路径整个丢掉了。与渠道库那条同一个道理 —— 池满时最老那份已经被清掉,
  点按钮的人得当场知道。这条路径不是纯 HTTP(拆分配置与 CLI 也调它),所以挂在
  `configureClaudeSplit` 的返回体上取走。

## 同一个形状的第五、六处:两扇切换门(直连与路由)

应用槽位修完之后拿同一支探针横扫其余写路径,又撞出两处 —— 而且是控制台上**最常用的两个按钮**
`POST /api/switch/:id`(直连某个渠道)与 `POST /api/router/:app`(切路由模式)。

两处的代码形状与本仓自己那条注释正好相反:

```js
switchClaude(prov);                                   // 先改客户端
withStoreRollback(() => { current[app] = prov.id; }); // 后写渠道库
```

`withStoreRollback` 回滚的是**内存**里的 `store/current`,回不到客户端那一边。所以渠道库落盘失败时:

| | 失败前 | 接口回 500 之后 |
| --- | --- | --- |
| HTTP | — | `{"error":"写入渠道库失败: simulated"}` |
| `~/.claude/settings.json`(两扇门都是) | `{"env":{"KEEP":"me"}}` | **已被改**:BASE_URL/AUTH_TOKEN 与槽位别名都写进去了 |
| 内存 / 盘上 `current` | `null` | `null`(withStoreRollback 这一半是对的) |

用户点的是"切换渠道",得到一句"写入渠道库失败",以为没切成 —— 实际客户端已经从原渠道被指到了
另一个地方。`/api/switch` 那一扇更隐蔽:它写进去的是**那个渠道的 base_url 与 api_key**,
也就是"客户端开始拿着 A 渠道的 key 打 A 渠道",而控制台里的"当前渠道"还停在旧的那个。

改法与前面几处一致,并把顺序收成**一份编排**(`applyClientSwitch`),三处调用共用:

1. 先把 `current[app]` 落盘(`saveStore`);失败时内存退回,客户端**一个字节都还没动**。
2. 再改客户端;失败时把 `current` 退回去并**写回盘上**。
3. 客户端那一步失败即"原子未生效"(`writeFileAtomic` 要么整份换新、要么原样不动),
   所以不需要旧内容快照。

`configureClaudeSplit` 原来那份自己写的两段式回滚也删掉了,改调同一条编排 —— 这是
"一个关注点一份实现"的直接好处:三扇门的先后顺序此后只有一处能改错。

顺带修掉一个被这次改动**暴露出来**的旧问题:编排里那一步把 `e.statusCode` 透传下去,
于是客户端配置自己的 4xx(settings.json 解析不了、ZCode 的 `wire_api` 不认识、没有可用渠道……)
不再被降级成 500。此前那条路上它们能拿到 400,是因为顺序是"先客户端、后渠道库",
客户端那步的 4xx 直接冒泡出去;**改成先落盘之后,它们会先撞上渠道库那一步的包装**。
注入 `S6 4xx 被吞成 500` 就是拿来钉这个的:三处校验类拒绝(合计 14 条断言)会一起变红。

## 切换门自己也会轮换备份,而它一句都没说

上面那条把预警接进了 `/api/claude/split` 与 `mixctl split`。同一支探针再往下走一层,翻出**同一个
漏法的根**:`/api/switch/:id` 与 `/api/router/:app` 这两扇门**自己就写渠道库**(`saveStore`),
池满时当场清掉最老那份备份 —— 而两扇门的响应体里**都没有 warnings**。控制台那两扇门本来就在用
`toastWithBackupWarnings`,是服务端没把话说出来。实测(探针,垫满 6 份备份后切一次):

```
池子: 5 份
[/api/switch] 这次切换里真被删掉的备份: 1 份
[/api/switch] 响应体 warnings: **没有(丢了)**
下一次 PUT /api/providers 的 warnings: ["…本次备份将顶掉 1 份 —— …-467-9a71…"]
  其中包含了上一次切换删掉的那份名字吗: 否
```

最后一行值得单独说:那次切换删掉的是 `-446-96bd`,而下一次写渠道库报的是它**自己**删的
`-467-9a71`。所以这不是"漏到下一次请求"那种暂存泄漏 —— **那句话就是没了**。
(暂存 `storeWarnings` 的"落盘前先清空"把上一次的残留兜掉了,这一层是对的;
缺的是"这一次的取走"。)

改法是在 `applyClientSwitch` 里取走那一份,与客户端配置那份**合成一个 `warnings` 字段** ——
调用方本来就在读这个字段,分成两个就要把每个调用点都改一遍,而"哪一份是谁的"对用户没有意义。

同一次扫查还证明了一件事:`configureClaudeSplit` 末尾原来还留着一句 `drainStoreWarnings()`。
它看着必要(那两处 `saveSlots`/`saveStore` 用同一个暂存),实际是**死代码** —— 本函数里那次
`saveSlots` 走的是不带 `backup` 的 `saveJson`,根本不产生预警。注入"删掉它"全绿,于是删掉了。

## 删渠道的失败点前移一步:第一段落盘就失败时,回滚根本没被触发

上一条把删渠道的**最后一处**回滚补齐了(三处状态一起快照、一起回滚)。同一支探针再往前挪一格,
发现**触发点前移**就绕过了整段回滚:

```js
if (slotChanged) saveSlots();     // ← 裸调,没有 try
if (routeChanged) saveRoutes();   // ← 裸调,没有 try
try { saveStore(); } catch (e) { /* 三处一起回滚 */ }
```

`saveSlots()` 抛错时,函数直接冒泡到 `apiHandler` 最外层那个只回 `e.message` 的兜底,而**四处内存**
(`store` / `current` / `slotMap` / `routes`)已经全改完了。实测(探针,让 `slots.json` 的原子替换
抛 `EIO`):

| | 删除前 | 接口回 500 之后 |
| --- | --- | --- |
| HTTP | — | `{"error":"simulated"}`(裸的,看不出是哪一步) |
| 内存 渠道 / 槽位 / current | `1` / `{provider: id}` / `id` | `0` / 已摘掉 / `null` |
| 盘上 `providers.json` | 渠道在 | 渠道在(这一步没碰过它) |
| 盘上 `slots.json` | 槽位在 | 槽位在 |

看起来"盘上没事",实际是**内存与盘上分叉了**:控制台里那个渠道已经不见了,而盘上还在;
重启之后它又回来,但绑它的槽位没了。三处落盘现在写在**同一个 `try`** 里,任意一步失败都走同一段回滚。

修的时候踩到一处**作用域**问题,值得记:`slotChanged` / `routeChanged` 两个标记原先声明在
`try` 内部,而回滚分支在 `catch` 里要读它们 —— 结果是 `routeChanged is not defined`(TDZ)。
两个标记的声明因此上提到 `try` 之前。这是"为了修一个错而引入另一个错"的典型,靠的是探针真的
跑了一遍回滚分支(让第二个标记指向的变量名出现在错误文案里)才看出来。

回滚里那两次落盘**只看 `slotChanged`/`routeChanged`,不看"失败在哪一步"**:盘上可能已经被前两步
写过(比如 `saveRoutes` 抛错时 `slots.json` 已经落了新的),所以只要这一轮改过就得写回旧值。

## 扫过但**没有**缺陷的写路径(如实记下来,免得下次重复扫)

同一支探针把 `mixrouter.js` 里所有会动内存状态的写路径过了一遍。这几处**试过之后是对的**,
写在这里是为了让下一个人不必再走一遍,也是为了说清"这一批覆盖到哪儿为止":

| 路径 | 造了什么失败 | 结果 |
| --- | --- | --- |
| `POST /api/providers`(新建渠道) | `providers.json` 原子替换抛 `EIO` | 内存与盘上都没变(走 `withStoreRollback`),错误文案已点名"写入渠道库失败" |
| `PUT /api/providers/:id`(改渠道) | 同上 | 同上 |
| `PUT /api/providers/:id` 带 `slots` 字段 | `slots.json` 原子替换抛 `EIO` | 返回 200 且内存没变 —— 因为渠道上的 `slots` 字段只是**渠道自带模型名**,与子代理槽位表(`slots.json`)不是一回事,这条路径根本不写那个文件 |
| `/api/sessions` 的钉定 / 解绑 / 清空 | — | 走 `saveSessionsSoon()`(1 秒防抖 + `unref` 定时器,失败经 `onError` 报一次),本来就不是"改了内存再落盘"的形状 |

**这四处是挨个读出来的,不是扫出来的** —— 判据是"读代码看这条路径有几处落盘、顺序如何"。
写路径一共十几处,这一批只把**会动内存状态**的那几条过了一遍。

## 单测里那个"恒真的断言":原值恰好等于新值时,回滚断言验不出东西

补这两条用例时踩到的,值得单独记:第一版用例跑**全绿**,而注入"客户端写失败时不回滚 `current`"
之后**仍然全绿**。原因是夹具的起点就不对 —— 同一个文件里前一条用例 `apply` 成功过,
`current.claude` 早就是 `@router` 了,于是"失败后要退回原值"里的原值**就是** `@router`,
断言恒真。

修法是夹具显式把起点退回直连态(内存与盘上 `providers.json` 的 `current` 一起设回 `null`),
并加一句自证"起点必须不是 `@router`"。改完之后同一批注入全部转红。

这是这一批里第二次遇到"断言写了、但验不出东西" —— 上一次是"落盘点不再清空暂存"那条
(写入在备份阶段就失败,预警还没暂存,断言是空的)。两次的形状不同(一次是窗口没打中,
一次是**原值恰好等于新值**),但都只有靠注入才能发现。

## 预警的出口:三扇门 + 一处非 HTTP 路径

渠道库的轮换预警要不要接进控制台,本来是个可以拖着不做的事(只进服务端日志也算"没丢")。
但上一条改动之后它变成了日常:池满以后**每保存一次渠道就轮换一次**,而用户的
"渠道库有备份"这句话其实只对最近 5 次成立。

接法是**取走即清**的模块级暂存(`storeWarnings`),不是改四个调用点的返回契约 ——
那四处形状各不相同,其中退出前的收尾落盘连 HTTP 都没有。

- 清空挂**两处**,都必要:`saveStore` 落盘前清一次,`drainStoreWarnings` 取走时清一次。
  只留取走那一次的话,两条**失败路径**(`withStoreRollback` 抛错 → `sendErr`、
  删渠道时 `saveStore` 抛错 → 把渠道放回去再 `sendErr`)是**不 drain 就返回**的,
  上一次那句"顶掉了谁"会漏进下一次**成功**写入的提示 —— 而那次操作根本没轮换过。
  挂在唯一落盘点上,这种漏法就结构性不可能。
- 出口四处:`POST /api/providers`、`PUT /api/providers/:id`、`DELETE /api/providers/:id`
  三个 HTTP 出口,加 `configureClaudeSplit`(被拆分配置与 CLI 两处调用,不是 HTTP 路径,
  所以在自己的返回体上带出去 —— 不取就会漏到下一次写渠道库的请求上)。
- 控制台四扇门都接(`public/index.html` 的保存 / 切换生效 Key / 启停 / 删除),
  复用 2026-09-26 那套 `toastWithBackupWarnings`。

## CI 上那条 Node 18 失败:已定位,是**夹具的夹具**在共享 runner 上不够用

上一版这里记的是"复现不出来,既不算已通过也不算已定位"。CI 补上了本机拿不到的那一块:
失败的用例是 `test/timeout-budget.test.js:198`
`流式:上游一滴一滴地发字节,也只有总 deadline 收得住`,报
`error: '实际:首字节超时(400ms)'`(run `36308749561`,Node 18)。有了用例名就能反查了。

**定位**:那套夹具把三段预算压到毫秒级(`MIXR_TOTAL_DEADLINE_MS=900`、
`MIXR_STREAM_FIRST_HEADER_TIMEOUT_MS=400`),而它的 `drip` 桩上游是这样发响应头的:

```js
res.writeHead(200, { 'content-type': 'text/event-stream' });   // 只是排队,还没上路
const t = setInterval(() => { res.write('data: 滴\n\n'); }, 150); // 头要等这第一跳才真的写出去
```

`writeHead` 之后不写字节,响应头就**不会**离开 Node 的写队列;它要等 `setInterval` 的
第一次回调(距 `writeHead` 150ms 上下)才随第一个字节一起上路。于是"上游给自己头"这件事实际发生在
**150ms + 调度延迟**处,而预算只有 400ms:余量 250ms,在 2 核、还同时在跑别的作业的
GitHub runner 上会被一次调度推迟吃干净 —— 运输层等不到响应头,先按**首字节超时**收了这条请求,
而断言里写着"这一条只可能是总 deadline 干的"。**判据本身没错,是夹具的时序假设不成立。**

本机把这一跳人为推迟到 400ms 之后,同一条失败一字不差地复现(`/tmp` 探针,未进仓库)。

同一次定位还量到**同一份文件里第二个余量不足的断言**:`r.ms < 700`(上面那条 `noHeaders`
用例)。本机并发跑全集时它报出 709–1027ms 的真实值 —— 定时器回调被调度推迟,预算 400ms
的任务实际在 700ms 之后才收尾。判据是"选的是 400ms 那一档、不是 4000ms 那一档",
上界贴到 700 就变成了在验"机器不忙"。

**改动**(只动 `test/timeout-budget.test.js`,产品代码一行未改 —— 这两条都不是产品缺陷):

- `drip` 桩在 `writeHead` 之后**立刻写一个字节**(`res.write(': 起流\n\n')`),
  响应头同步上路。150ms 的心跳原样保留:它要产生的是"字节在流动、空闲看门狗被反复重置"。
- `noHeaders` 那条的上界从 700ms 放宽到 2000ms。真退化成非流式档会得到 ~4000ms,仍然红。

## "夹具在负载下才露出来的失败"是一族,不止这两条

顺着上面那条往下扫,用**并发跑全集**做压力(本机 8 核,每轮 10 份并发、共 60 份),
在**改动前的冻结副本**上量到 **35/60 份失败**,集中在三条:

| 用例 | 失败份数 | 报出来的错误 | 真实原因 |
|---|---|---|---|
| `流式:上游一直不发响应头…` | 30 | `要在流式首字节预算(400ms)附近收,实际 709–1027ms` | 上界贴死 700ms |
| `加权池:冷却中的成员退出轮转…` | 17 | `冷却期内全部落到 pb` | 冷却写成 `Date.now() + 60`,而 4 次串行请求在负载下会耗过 60ms,冷却自己过期了 |
| `M4 短在途请求被等完…` | 在 CI 日志里出现过 | `release is not a function` | `await sleep(60)` 之后就用 `release`,而它由处理函数赋值;这 90ms 总预算在负载下不够 |

三条的症状都**指错方向**:第二条听起来像加权策略坏了,第三条听起来像 `lifecycle` 有 bug,
而实现两处都是对的。这是这批夹具真正的毛病 —— 不是"偶尔红",是"红的时候把人引到错的地方"。

**改动**:

- 新增 `test/wait-for.js`:`waitFor(predicate, { label, timeoutMs })`。夹具里"等某件事发生"
  一律改用它,判据落在**心跳**上而不是一个乐观的毫秒数,超时信息直接说明等的是什么。

## 循着同一批失败查出来的**产品缺陷**:会话绑定落盘(`lib/routing/sessions.js`)

上面那轮并发里,`test/audit-fixes.test.js` 也炸过一次,报的是
`sessions.json.<ms>-<hex>.tmp` 的 `EACCES`。那个 EACCES 是**测试夹具自己**造的
(`audit-fixes` 有一条用例专门让渠道库写不进去),不是产品缺陷 —— 但它顺出来的这条是真的:

**三个缺陷,都在会话绑定的落盘上。**

### 一、`dirty` 在写成功**之前**就被清掉(改动丢一次就永远丢了)

```js
function flush() {
  if (!dirty) return;
  dirty = false;                                  // ← 先清
  saveJson(sessionsFile, { version: 1, bindings }); // ← 后写
}
```

写失败时这次改动已经被记成"落过盘"了。后果不是"这一次没写进去",而是**以后也不会再写**:
内存里那份改动还在,盘上永远是旧的,而没有任何提示。
实测(探针,`/tmp` 未进仓库):第一次 `flush()` 抛 `EACCES` 之后,手动再 `flush()` 一次
**不写任何东西** —— 这份改动永远不会落盘。

改成写完再清。抛照旧抛出去:关停路径(`onFlush`)要能看见这次没落成。

### 二、去抖那一次的失败没人接得住,直接是个 uncaughtException

```js
timer = setTimeout(() => { timer = null; flush(); }, 1000);   // flush 抛 → 裸 timer 抛
```

冷启动的探针里,进程从 `Timeout._onTimeout` 冒出一个未捕获异常。常驻进程有个
`uncaughtException` 兜底只记日志,所以进程不死 —— 但这次改动**再也不会落盘**(见上一条),
两件事叠在一起最难查。

改成 `try { flush() } catch (e) { reportSaveError(e) }`,`dirty` 留在 `true`,
下一次自然落盘(下一次 `saveSoon`,或关停时的 `flushSessions`)会把它带上。
`reportSaveError` 由调用方注入(库不该决定日志长什么样),`mixrouter.js` 接上本进程的格式。
**不自动重排定时器**:落盘失败多半是磁盘满/权限这类持续性故障,一秒一次的重试只会把日志刷满。

### 三、三扇门"说成功、却没落盘"(接口回 200 的同一刻盘上还是旧的)

`DELETE /api/sessions`、`POST /api/sessions/:key/pin`、`DELETE /api/sessions/:key`
以前都是 `改内存 + saveSessionsSoon()` 然后**当场回 200**。`saveSoon` 是 1s 去抖的后台定时器,
所以接口说"已清空"时盘上一条不少;那一秒里的落盘失败又没人接得住(见上一条)。

修好前两条之后这条**仍然存在**,而且暴露出第三个原因:`flush()` 只看 `dirty`,而 `dirty`
只由 `saveSoon()` 点亮 —— 这三扇门直接改内存,根本没点亮它。实测(探针让原子替换抛 `EACCES`):

```
DELETE /api/sessions → 200 {"ok":true,"cleared":true}
内存里还剩 0 条        ← 说成功
盘上还有 2 条          ← 什么都没变,重启全部复活
期间抛出的事件: [ uncaughtException: EACCES ]
```

改动:

- `flush(force = false)`,`force` 绕过 `dirty`。`mixrouter.js` 新增 `flushSessionsNow()`
  (即 `flush(true)`),只有"确知内存刚被改过"的调用方用它;退出路径仍走普通 `flush()`。
- `mixrouter.js` 新增 `mutateSessions(mutate)`:改之前整份快照绑定表(`new Map(sess.sessions)`),
  改完立刻同步落盘;落盘失败就把内存整份退回去,再如实回 5xx。
  绑定表在内存里就是个 Map,整份快照的代价可以忽略,而回滚是精确的 —— 不需要逐项逆操作。
- **钉定那一扇门改的是副本,不是原地改**。`s` 是绑定表里的那个对象,原地改的话
  "整份退回引用"退回去的还是被改过的它。会话记录里那几个字段都是标量,`{ ...s }` 就够。
  这一条有专门的注入验过(见下)。

修好之后同一份探针:

```
DELETE /api/sessions → 500 {"error":"写入会话绑定失败: EACCES: permission denied, open"}
内存里还剩 2 条        ← 回滚了
盘上还有 2 条
期间抛出的事件: (一个都没有)
```

这一批里有**一发故意留绿**:`drip` 桩上游那个夹具改动本身是**消除时序假设**,单跑时负载
不足以让它红。它的鉴别力不由注入证明,而由"把桩 flush 响应头那一跳人为推迟到预算之后,
能一字不差复现 CI 那条失败(`error: '实际:首字节超时(400ms)'`)"来证明 —— 如实记下来。

会话那三条注入第一轮跑出来是 **GREEN**,那是**新写的判据还不够**的信号:库层那三个失败面
当时只用 HTTP 路径覆盖,而 HTTP 路径在 `dirty` 为假时根本走不到 `flush` 的那两个分支。
补了 `test/routing-modules.test.js` 里三条直接对库的用例之后才转红。
**注入绿了要去补判据,不要去怀疑注入。**

## 仍未覆盖的边界

- **会话绑定落盘的失败面只在"原子替换抛错"这一种成因下验过**。磁盘满、目录只读、
  临时目录被清掉……都走到同一个 `saveJson` 抛错,行为应当一致,但没有逐种造过。
- **`saveSoon` 的去抖失败之后不重排定时器**,靠的是"下一次落盘会带上"。而"下一次"可能是
  一秒后、也可能要等到关停 —— 中间这段时间盘上是旧的。这是有意的(见正文的取舍),
  但意味着进程若在这段窗口里被 `SIGKILL`,改动就丢了。这一条没有用例(要造出来得
  精确控制进程被杀的时刻)。
- **并发跑全集必须在冻结副本上跑这件事没有机制保证**。这次是因为在改的工作树上跑了,
  量出 5 份无法解释的失败才发现的。仓库里没有任何东西阻止下一次这么做。
- **`waitFor` 是逐个夹具换过去的**,只覆盖了本轮量到会红的那三处。
  `test/*.test.js` 里还有十几处"小 sleep 之后立刻用某个异步才产生的状态"的写法
  (见 `await sleep(N)` 的搜索结果),哪些够用、哪些不够用没有系统性的检查 ——
  判据仍然是"跑 60 份并发看不看得见红"。
- **渠道库的备份只在 `saveStore` 这一条路上**。`providers.json` 现在只有这一个写入点
  (`grep PROVIDERS_FILE` 可核),所以覆盖是完整的;但若将来出现第二条写它的路径
  (比如某个脚本直接改盘),备份不会跟着走 —— 这一条靠的是"只有一个写入点"这个事实,
  没有机制强制。
- **`keep` 是硬编码的 5**,与 `lib/config-backup.js` / `lib/backup/inventory.js` 三处同值,
  由测试断言钉住(不是 `require` 过来的,`atomic-write` 是被谁都 require 的底座,
  顶层引 `config-backup` 会把 backup 那条链绑进每个用户的 require 图)。改上限要改三处。
- **渠道库备份的轮换预警会报进控制台,但"渠道库有备份"这件事没有任何面板入口**。
  `GET /api/backups` 的 `[data]` 池能查到,控制台里没有对应视图 —— 用户要自己知道去
  哪儿看。(`/api/backups` 的 `[data]` 格此前恒为 0,现在会真的报数,这一条有用例。)
- **`configureClaudeSplit` 的 `warnings` 仍没有用例**。客户端配置那一份现在也接住了
  (`switchClaudeRouter` 的返回值),但"取到的那句话会走到谁手里"没有验 ——
  这条路径被拆分配置与 CLI 两处调用,两处都不是 HTTP,没有可断言的响应体。
  已有的断言只覆盖"渠道库落盘失败时整体回退"与"客户端写失败时回退 `current`",
  不覆盖"预警有没有被带出去"。
- **删渠道的失败回滚在"回滚自己也失败"时只能如实报错**,不做补偿。那时盘上是不一致的
  (槽位/路由已改、渠道库未改),响应里会说明并让用户去查两个文件 —— 有用例覆盖"回滚成功"
  那条路,没覆盖"回滚也失败"那条(要造出来得让 `saveSlots` 与 `saveStore` 同时失败)。
- **"先动客户端、后写渠道库"这个形状此后再犯要有用例拦**,但**判据是靠"改动的那一行"
  而不是靠机制**。现在三扇门共用 `applyClientSwitch`,只要有人不经过它直接写
  `current[app] = …` 就绕过了。仓库里没有"禁止直接赋值 `current`"这类检查 ——
  这一条靠的是"当前只有三处切换路径"这个事实。
- **预警出口是"逐个接"的,没有机制保证接全**。这一批接的七处:控制台四扇门
  (保存/切换生效 Key/启停/删除)、应用槽位按钮、`mixctl split`、`mixctl route`,
  加上服务端的两扇切换门自己产出的那一份。判据是"读代码看返回体里有没有 warnings
  被用到 + 哪几条路径会写渠道库"—— 新增一扇门时不会有人提醒你。已有用例覆盖这七处;
  **其余消费 warnings 的地方(如果有)没有系统性的检查**。
- **`warnings` 只有一个 `console.warn` 之外的出口(响应体),没有持久化**。服务端日志
  里有(备份池那层打的),但"这一次请求顶掉了谁"与请求的关联只存在于这一次响应里 ——
  关掉弹窗就没了。这一条是有意的(不落盘就不必考虑脱敏),但意味着它不能事后追查。
- **扫过的写路径**是:`withStoreRollback`、`configureClaudeSplit`、删渠道、
  `PUT /api/slots`、`PUT /api/routes`、`/api/switch`、`/api/router` 七处
  (`/api/providers` 的增改、`/api/zcode` 的渠道写、`flushSessions` 的落盘形状不同,
  未逐条验"失败时内存是否回滚")。这七处是挨个读出来的,没有系统性的检查。
- **`configureClaudeSplit` 的回滚在"回滚自己也失败"时只能如实报错**。客户端那一步
  已经有一句(`…;回退渠道库也失败: … —— 盘上已不一致`),渠道库那一步的 `saveSlots`
  回滚失败则只被 `catch {}` 吞掉并附一句注释 —— 那时盘上 slots 与内存不一致,而响应里
  不会说。要造出来得让 `saveSlots` 与 `saveStore` 同时失败。
- **`purgeTmpSiblings` 只清比对中的那一个目标**。盘上别的目标的临时残留不在它的范围里,
  也无人在清 —— 那是有意的(清理是"顺手"而非"清扫"),但意味着残留仍可能在别的目录里堆积。
