# 2026-09-20

本次把已有的 `lib/routing/explain.js` 从"策略看起来可预测时才给个候选"重写为**按真实转发顺序重放**,
并新增两个只读入口:`mixctl explain` 与 `POST /api/routing/preview`(基线 `5b77247f` 上只有解释器模块,
没有任何 HTTP 暴露面)。以下只记录本次实际改动与实跑结果,不对应补造的历史版本或里程碑。

## 只读诊断的语义对齐

预览此前与真实转发在多个分支上不一致。本次按 `proxyHandler` 的选择顺序对齐,并把"为什么"写进结果:

- **兜底路由**用 `{id:'default', strategy}` 作为 effective rule:`round_robin` 读 `pools.default` 游标
  (不是 `pickMember(null)` 的 `_` 游标),`weighted` 读 `__w_default` 当前余量;
  `priority` 取池序首个可用(主渠道冷却时降级)。
- **内容分流(`when.body` 命中)**在 kind 过滤后直接取第一个成员,不跑池策略、不走会话粘性;
  冷却与健康状态不改变这个首选,`random` 配置同样给确定首选。
- **会话粘性**与 **手动钉定**分开处理:钉定只检查"本组渠道存在、启用、不在冷却",
  不要求属于原池、不检查熔断(真实路径就是这样);槽位请求不被池外钉定劫持。
  普通粘性必须在 kind 过滤后的成员里且通过健康/冷却。
- `least_used` 的活跃会话数与粘性判定共用**同一份剪枝后的会话副本**:先按 `now-lastUsed > ttlMs`
  过期 TTL,再按 `lastUsed` 升序淘汰到 `max`(同时间戳按原 Map 插入顺序)。原会话表与对象不被触碰。
- `random` 在多个可选成员时**不调用 RNG**且 `predicted` 为 `null`;只有一个可选成员时给出确定首选。
- **钉定分支不重跑 kind 过滤**:池外钉定只做「本组存在、启用、不在冷却」三项检查,所以 `kind:'chat/completions'` 时它照样可能落到 `wire_api:responses` 的渠道——这正是真实路径的行为(已用真实转发核实,见下文),不是预览的偏差。

## 输出上限与脱敏

- `candidates` / `effective` / `selection.candidates` / `matched.rule.pool` / `ghosts` /
  `kindFilter.kept` / `kindFilter.dropped` 每个展示数组都受 `maxCandidates` 约束,并在
  `limits.arrays[字段]` 里给出 `total/shown/omitted`,同时发 `warnings`;不再静默截断。
- 失败分支(`provider_disabled` / `wire_api_mismatch` / `no_route`)同样带 `warnings` 与 `limits`,
  不会因为 `ok:false` 丢掉诊断元数据;`limits.rulesTraced/rulesOmitted/truncated` 的计数不受展示截断影响。
- 渠道字段走白名单(`id/name/model/models/wire_api/ua/enabled/slots`);`base_url`、`api_key`、
  `keys`、`active_key`、请求头原文与输入 token/bodyText 原文都不出现在结果里,
  `when.token` 只回显 `{present,len}`。

## 接线与 CLI

- `mixrouter.js` 新增只读装配 `explainRoute` 并导出;它不经 `/api/state`、不传 `sessionList`/`prune`/`save`
  这类会改会话表的入口,而是注入只读的 `sessionSnapshot()`。`POST /api/routing/preview` 复用
  `readObject` 的 JSON 对象校验与跨站闸门,HTTP 状态取 `ok ? 200 : error.httpStatus`。
- `mixctl explain <claude|codex> <model> [--kind] [--session] [--json]` 与
  `mixctl explain --input <file|-> [--json]`,两种形态互斥。不动原有的 `api`/`apiPost`。
- 参数错误(app/kind/session/未知与重复选项/选项缺值)一律在发 HTTP **之前**失败;
  `--token` 之类的明文凭据选项直接拒(凭据只属于请求体,不该出现在 `ps` 可见的 argv 里)。
- 新的 HTTP helper:总时限 5s(不随零碎响应续期)、响应体积上限 2 MiB、输入上限 1 MiB、
  JSON 解析与 `ok/error` 形状校验。失败时 `--json` 也输出可解析对象并 exit 非 0。

## 修掉的三个缺陷

- **响应被截断与"连不上"分不开**:服务器中途 reset 时 `req` 的 `error` 常先于 `res` 的 `close` 到达,
  原实现无条件报 `request_failed`(文案是"无法连接本机路由预览接口"),把已经建立连接、
  只是没读完的情况说成连不上。现按"是否已收到响应头"与 socket 错误码分开:
  已收到响应头 → `response_aborted`;未收到且为 `ECONNRESET`/`EPIPE`/`ERR_STREAM_PREMATURE_CLOSE`
  → `connection_reset`;其余才是 `request_failed`。
- **`selection.candidates` 被压成单元素,丢了预览原有语义**:基线里它是
  `effectiveMembers.slice(0, maxCandidates).map(m => m.provider.id)`——**候选池**;
  重写时改成了 `picked ? [picked] : effectiveMembers`,于是 content / sticky / pinned /
  deterministic-strategy 四个分支只要有首选,候选列表就只剩那一个,`limits.arrays` 里的总数
  也跟着变成 1。现统一回"kind 过滤后的有效成员池,只为展示截断":`predicted` 才是这一条请求的首选,
  钉定可以选池外渠道,那时 `predicted` 故意不在 `candidates` 里(note 已说明),不能因此缩窄候选池。
- **`test/routing-preview-api.test.js` 的槽位用例夹具错**:该用例想核"槽位存在但没绑渠道"的回落提示,
  但沿用了 `beforeEach` 里 `match:'x'` 的规则,而探针模型名 `mixr-empty` 本身含 `x`,
  于是普通规则先命中,断言 `matched.via === 'default'` 必然失败。行为是对的,夹具是错的:
  该用例改用不会命中的 `match`,并补 `matched.ruleId === null` 明示"确实落到了兜底"。

### 钉定 + `chat/completions`:已由独立探针核实(原先列为最大覆盖缺口)

"钉定绕过 kind 过滤"此前被列为最可能出错的一处,只有代码阅读证据。主会话随后用真实 `proxyHandler`
加 mock 上游写了独立探针(不进仓库树)直接对照预览与真实转发,三种组合全部一致:

| 组合 | 真实转发 | 预览 |
| --- | --- | --- |
| A 钉定到池外 `wire_api:responses` 渠道,池里只有 chat 成员 | 首发命中该 responses 渠道,上游收到 `/v1/responses`、model=钉定 model,客户端 200(代理自己翻译 chat→responses) | `source:'pinned'`、`predicted:'resp'`,一致 |
| B 钉定到池外 chat 渠道(对照) | `/v1/chat/completions` → chat2 | `predicted:'chat2'`,一致 |
| C 池里全无 chat 成员 + 钉定 | 在会话解析之前 400 `wire_api_mismatch_error`,零上游命中 | 同样 400 同码,一致 |

**结论:钉定绕过 kind 过滤是真实路径的行为,不是预览的偏差。** 谁把 `lib/routing/sessions.js` 的钉定分支
改成再跑一次 kind 过滤,谁就把预览改成了不忠实——`test/routing-preview-api.test.js` 新增的两个用例
就是拿来挡这一手的,注释里也写明"这是照抄真实路径的忠实行为"。反向注入"钉定分支再过滤一次 kind"
确认该用例会红。证据:`evidence/main-pinned-kind-probe.test.js`、`evidence/main-pinned-kind.log`、
`evidence/main-pinned-kind-report.json`。

## 仍未覆盖的边界

(原先挂在这一节的"钉定 + `chat/completions`"已上移为已覆盖项,见《钉定 + `chat/completions`:已由独立探针核实》;
这里保留的是确实还没覆盖的。)

- 固定对照探针**不覆盖** `selection.candidates`:把该字段压回单元素后探针 28/28 全绿,
  只有 `routing-preview-api` 会红。探针比的是"首选渠道与真实转发是否一致",候选池完整性与它正交,
  改动这一带时不能只看探针绿。
- `mixctl explain` 的 5s 总时限与 stdin 5s 读取时限是真实等待,两个用例共占约 10s;
  CI 上跑全量时这段是纯等待。
- 预览只解释**当前快照**的首选:不保证上游成功,也不预测重试后的落点。
  `random` 多候选时不预测是刻意的(不取随机数),没有"给个概率"的输出。
- `weighted` / `round_robin` 的预测基于当前游标/余量,预览不消耗它们;实跑会前移,
  连续两次 `explain` 给同一答案是预期的,不代表两次实跑会落到同一渠道。
- 预览不校验渠道凭据是否有效,也不探测上游可达性——`wire_api`、`enabled`、冷却与熔断之外的健康细节不在其中。
